Guía de configuración: ClickHouse Cloud

Paso a paso de todo lo que hay que configurar para poner en marcha el camino ClickHouse Cloud del flujo de eventos STB: qué le toca al dispositivo, qué le toca a la tubería de Kafka que ya está decidida (Broker → Bridge → Worker de enriquecimiento), y qué le toca a la consola de ClickHouse Cloud — creación del servicio, tablas, ClickPipes y usuarios.

Sobre "crear una función de Kafka"

💡

Aclaración antes de empezar: Kafka en sí no tiene "funciones" — es una cola de mensajes, no un motor de cómputo. Lo que sí existe, y probablemente es a lo que se refiere la pregunta, son dos cosas distintas y es importante no confundirlas:

  1. El Bridge y el Worker de enriquecimiento — dos piezas de software que el equipo construye (no vienen de ningún proveedor) para mover los eventos desde MQTT hacia Kafka y para enriquecerlos antes de que lleguen al destino final. Esto ya está decidido en el diseño actual y se explica en la sección de la tubería Kafka más abajo.
  2. ClickPipes — el conector administrado que ClickHouse Cloud ofrece para leer un tópico de Kafka y escribirlo en una tabla, sin tener que instalar Kafka Connect por separado. Es la pieza más parecida a "una función de Kafka" del lado de ClickHouse Cloud, y es el foco de la sección de ClickPipes en esta guía.
Si la pregunta apuntaba a otra cosa — por ejemplo una Cloud Function separada para el Worker de enriquecimiento — avisa y se ajusta esta guía; por ahora se cubren las dos interpretaciones más probables.

1. Qué hay que hacer en el STB

no cambia según el backend elegido
Esto es lo mismo sin importar si al final se usa ClickHouse Cloud, BigQuery o cualquier otro motor — el STB nunca habla directo con la base de datos.
  1. Cliente MQTT ligero en el firmware que arma el evento (JSON pequeño) y lo publica a un solo endpoint fijo: el Broker MQTT. El STB no necesita saber qué hay después del Broker.
  2. Identidad de dispositivo: cada STB se autentica contra el Broker. Lo más robusto es un certificado único grabado en fábrica/aprovisionamiento (mTLS); más simple de operar (y más fácil de rotar) es un usuario/API key asociado al número de serie del equipo.
  3. Cola local + reintentos: si el STB pierde conectividad, debe guardar eventos en un buffer local (memoria/flash) y reintentar cuando vuelva la red, para no perder datos.
  4. Agrupar y comprimir antes de enviar cuando sea posible (varios eventos por mensaje, payload comprimido) — reduce el número de conexiones y el tránsito, sin cambiar nada del lado del servidor.

2. La tubería Kafka (ya decidida)

Broker → Bridge → Worker de enriquecimiento
Estas piezas ya están definidas en el diseño actual y no dependen de qué backend final se use — son el mismo transporte para ClickHouse Cloud, BigQuery o cualquier otra opción.
El Worker de enriquecimiento es el lugar natural para normalizar campos, resolver IDs y descartar eventos inválidos antes de que lleguen a ClickHouse Cloud — así ClickPipes solo escribe datos ya limpios.

3. Crear el servicio en ClickHouse Cloud

consola web · clickhouse.cloud

Alta del servicio

Una cuenta y unos clics en la consola — no hay servidores que aprovisionar a mano

  1. Crear cuenta en la consola de ClickHouse Cloud y dar de alta un método de pago (tiene periodo de prueba gratuito con crédito limitado).
  2. Elegir nube base (AWS, GCP o Azure) y región — conviene la misma nube/región donde ya corre el resto de la tubería (Kafka/Bridge/Worker), para minimizar latencia y costo de tránsito entre nubes.
  3. Elegir el tier del servicio (ver tabla de abajo) — para producción real con alta disponibilidad, el mínimo recomendable es Scale.
  4. Confirmar y esperar el aprovisionamiento — toma unos minutos, no hay instalación manual de software.
Qué NO hay que hacer
Instalar ClickHouse, configurar ClickHouse Keeper, ni levantar balanceador de carga — todo viene incluido en el servicio.

4. Crear la tabla

motor MergeTree
  1. Crear la tabla con motor MergeTree normal, particionada por fecha — no hace falta pedir ReplicatedMergeTree como en una instalación propia.
  2. ClickHouse Cloud la reescribe internamente a SharedMergeTree: guarda los datos en almacenamiento compartido (S3/GCS) en vez de en el disco de cada nodo, así cualquier réplica de cómputo puede leer cualquier parte de la tabla sin copiar datos entre réplicas.
  3. Definir TTL (tiempo de retención) sobre la tabla si no se quiere guardar todo el histórico ahí — por ejemplo 90 días, dejando el histórico completo en BigQuery/GCS como se plantea en el reporte de arquitectura híbrida.
ℹ️

Corrección sobre un reporte anterior: el reporte "Arquitectura de Ingesta de Eventos" mencionaba crear la tabla en ClickHouse Cloud con ReplicatedMergeTree. Ese motor es el correcto para una instalación propia multi-nodo; en Cloud el paso correcto es crear MergeTree simple y dejar que el servicio la convierta a SharedMergeTree — ya se corrigió ese reporte para reflejar esto.

5. Configurar ClickPipes

Data Sources → ClickPipes → New Pipe → Apache Kafka
Esta es la pieza que conecta el tópico Kafka enriquecido con la tabla de ClickHouse Cloud — sin instalar Kafka Connect por separado.
  1. Dentro del servicio, ir a Data Sources → ClickPipes → New Pipe y elegir Apache Kafka como origen.
  2. Capturar los datos de conexión: Broker (host:puerto, ej. kafka.totalplay.local:9092), Topic (el tópico enriquecido, ej. tv-events-enriched) y Consumer group.
  3. Elegir el método de autenticación según cómo esté expuesto el Kafka propio: SASL/PLAIN + TLS, SASL/SCRAM-SHA-256 o SASL/SCRAM-SHA-512 (cuál está disponible depende de la configuración del Broker).
  4. ClickPipes detecta el esquema automáticamente a partir de los mensajes (JSON o Avro) — se pueden ajustar tipos/nombres de columna antes de confirmar.
  5. Elegir si ClickPipes escribe a una tabla ya existente (la del paso 4) o si la crea automáticamente a partir del esquema detectado.
  6. Guardar y activar el pipe — queda corriendo de forma continua, con su propio monitoreo en la consola (lag de consumo, filas escritas, errores).

6. Usuarios, roles y redes

  1. Crear un usuario/rol dedicado para ClickPipes (solo permisos de escritura sobre la tabla de eventos) y usuarios de solo lectura para quien consulte desde BI/dashboards — nunca compartir el usuario administrador.
  2. TLS viene activado por defecto en la conexión a la consola y al endpoint de consultas — no hay que configurarlo aparte.
  3. Redes privadas (conexión sin salir a internet pública, tipo Private Link/VPC peering) están disponibles desde el tier Scale en adelante — relevante si el Kafka/Bridge/Worker corren dentro de una VPC privada.

Checklist de orden recomendado

  1. 1STB: cliente MQTT, identidad de dispositivo, cola local — no depende de nada de lo de abajo. equipo firmware
  2. 2Broker MQTT + Bridge + Worker de enriquecimiento: ya decididos, deben estar corriendo antes de conectar ClickPipes. equipo backend
  3. 3Crear el servicio de ClickHouse Cloud (nube, región, tier Scale). consola CH Cloud
  4. 4Crear la tabla con MergeTree + TTL si aplica. consola CH Cloud
  5. 5Configurar ClickPipes apuntando al tópico enriquecido, validar que las filas empiezan a llegar. consola CH Cloud
  6. 6Usuarios/roles de escritura (ClickPipes) y lectura (BI) por separado. consola CH Cloud
  7. 7Piloto con unos cientos de STB reales antes de escalar al total de dispositivos — para validar que el diseño aguanta el volumen real.
