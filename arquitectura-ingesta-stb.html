Cómo configurar cada opción para recibir eventos de STB

Qué se necesita preparar en cada una de las 5 opciones (BigQuery, DynamoDB, ClickHouse, ClickHouse Cloud y Aurora) para poder recibir los eventos del Set-Top Box, y qué le toca hacer al Set-Top Box en cada caso. Aquí el foco es cómo se construye, no cuánto cuesta — el costo está en otro reporte.
🔑

La idea más importante de todo este documento: en ninguna de las 5 opciones el STB debe conectarse directamente a la base de datos. Ni BigQuery, ni DynamoDB, ni ClickHouse (autoalojado o Cloud), ni Aurora están pensados para que millones de dispositivos les hablen directo — necesitan credenciales de nube (GCP/AWS) que jamás deberían vivir en el firmware de un STB. Todas pasan primero por un gateway de ingesta propio. Por eso el trabajo del lado del STB es prácticamente el mismo sin importar cuál base se elija — lo que cambia es lo que se construye del gateway hacia adentro.

Qué hay que hacer en el STB

aplica igual a las 5 opciones
Esto es lo que responde directamente a "qué se configura en el STB" — y es prácticamente idéntico sin importar la base final.
  1. Un cliente HTTP(S) o MQTT ligero en el firmware que arma el evento (JSON pequeño) y lo manda a un solo endpoint fijo — el gateway de ingesta. El STB nunca necesita saber si el destino final es BigQuery, DynamoDB, ClickHouse o Aurora.
  2. Identidad de dispositivo: cada STB necesita autenticarse. Lo más robusto es un certificado único grabado en fábrica/aprovisionamiento (mTLS); más simple (y más fácil de rotar) es un API key o token asociado al número de serie del equipo.
  3. Cola local + reintentos: si el STB pierde conectividad, debe poder guardar eventos en un buffer local (memoria/flash) y reintentar el envío cuando vuelva la red, para no perder datos.
  4. Envío por lotes (batching): agrupar eventos cada 30–60 segundos (o cada N eventos) en vez de mandar uno por uno — reduce drásticamente el número de conexiones, y beneficia a los 5 backends por igual.
  5. Compresión del lote (gzip) antes de enviarlo — a 75M eventos/día el tráfico de red agregado es real.

Configuración del lado del servidor, por proveedor

Lo que hay que instalar/crear en cada opción, más allá del STB.

BigQuery

Ya lo usan hoy — falta construir la capa de ingesta, la base en sí no cambia de forma

  1. Crear la tabla particionada por fecha y clusterizada por los campos que más se van a filtrar (ej. stb_id, event_name) — sin esto, el costo de consultar se dispara.
  2. Crear una service account con el rol mínimo (roles/bigquery.dataEditor), solo para el pipeline — nunca para los STB.
  3. Habilitar la Storage Write API en el proyecto.
  4. Levantar un endpoint receptor (Cloud Run o API Gateway) que publique a Pub/Sub.
  5. Una suscripción (Dataflow o Cloud Function) consume de Pub/Sub y escribe a BigQuery en lotes vía Storage Write API.
Piezas adicionales
Cloud Run/API Gateway (receptor) · Pub/Sub (buffer) · Dataflow o Cloud Function (consumidor)
Complejidad
Media

DynamoDB

La tabla es rápida de crear; lo que toma tiempo es adoptar el stack de IoT de AWS

  1. Diseñar bien la partition key + sort key (ej. stb_id / event_timestamp) — es la decisión que más define cómo escala la tabla.
  2. Modo de capacidad On-Demand para empezar, sin estimar RCU/WCU.
  3. Configurar TTL si se quiere expirar eventos viejos sin costo de borrado manual.
  4. Dar de alta cada STB en AWS IoT Core con su certificado X.509 único (el patrón nativo de AWS para flotas de dispositivos, en vez de un API Gateway genérico).
  5. Configurar una regla de IoT Core que enrute los mensajes MQTT hacia DynamoDB (directo, o vía Kinesis si se quiere buffer y reintentos).
Piezas adicionales
AWS IoT Core (identidad + transporte) · Kinesis Data Streams (buffer, opcional) · Lambda (transformación)
Complejidad
Media-alta

ClickHouse (autoalojado)

Nada viene administrado — es la opción con más piezas que instalar y mantener tú mismo

  1. Provisionar las VMs (ej. 3 nodos, 8 vCPU/32 GB) e instalar ClickHouse Server (paquete oficial o Docker).
  2. Configurar ClickHouse Keeper (el reemplazo de ZooKeeper) para coordinar el clúster.
  3. Crear la tabla con motor ReplicatedMergeTree, particionada por fecha, más una tabla Distributed encima para repartir queries entre nodos.
  4. Levantar Kafka (o Redpanda) delante de ClickHouse, y crear una tabla con motor Kafka que auto-consume del tópico — el patrón estándar de ingesta masiva en ClickHouse.
  5. Configurar usuarios/roles y TLS para las conexiones, y un balanceador de carga delante del clúster.
Piezas adicionales
Kafka/Redpanda (buffer + desacople) · ClickHouse Keeper (coordinación) · balanceador de carga
Complejidad
Alta

ClickHouse Cloud

Mismo motor que arriba, pero sin instalar/operar nada — ClickHouse Inc. corre el servidor

  1. Crear un servicio en la consola de ClickHouse Cloud, eligiendo nube (AWS/GCP/Azure) y región, y el tier Scale (necesario para alta disponibilidad real — Basic corre en una sola réplica).
  2. Crear la tabla con motor ReplicatedMergeTree, particionada por fecha — la parte de replicación/coordinación (equivalente a Keeper) ya la maneja el servicio.
  3. Configurar ClickPipes (el conector Kafka nativo administrado) apuntando al tópico enriquecido — no hace falta levantar Kafka Connect ni nada externo.
  4. Definir usuarios/roles desde la consola; TLS y balanceo ya vienen incluidos en el servicio.
Piezas adicionales
Ninguna propia — ClickPipes y la coordinación del clúster ya vienen incluidos en el servicio
Complejidad
Media

Amazon Aurora

El motor es fácil de crear; diseñar bien para escritura masiva es lo que exige cuidado

  1. Crear el cluster Aurora Serverless v2 (PostgreSQL o MySQL-compatible), definir rango mínimo/máximo de ACU.
  2. Diseñar el esquema con pocos índices — cada índice extra penaliza el insert, y aquí el insert es lo crítico.
  3. Configurar RDS Proxy delante del cluster — sin esto, con millones de STB se agotan las conexiones casi de inmediato.
  4. Levantar la capa de ingesta (API Gateway + Lambda, o un servicio en ECS) que agrupe escrituras antes de mandarlas al proxy.
  5. Security Groups/VPC configurados para que solo ese servicio — nunca el STB — pueda conectarse a la base.
Piezas adicionales
RDS Proxy (obligatorio a esta escala) · API Gateway + Lambda o ECS (capa de ingesta)
Complejidad
Media-alta

"Complejidad de puesta en marcha" es una comparación relativa entre las 5, no un número de semanas — depende del tamaño del equipo y de cuánto de esto ya exista. Antes de comprometerse con una opción, vale la pena un piloto chico (unos cientos de STB reales) para validar que el diseño aguanta antes de escalar al total de clientes.

Notas: esta guía describe patrones de arquitectura estándar y ampliamente documentados para cada plataforma (no son inventados para este caso), pero no reemplazan una prueba de carga real con el volumen y payload exactos que definan los devs de STB. Los nombres de componentes son los servicios nativos de cada nube (GCP para BigQuery, AWS para DynamoDB/Aurora); para ClickHouse autoalojado, la elección de nube es libre. El endpoint/gateway de ingesta es responsabilidad propia en los 5 casos — ninguna de las 5 plataformas lo provee por sí sola.
